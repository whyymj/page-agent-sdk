# Proposal: imperative-zero-tool-gate(操作指令零工具收尾门禁,防「谎报完成」)

> 状态:**规划完成,未实施**。优先级 P1。测试用例集 C-13 的机制化方案。与完结门禁(防提前收口)、resumeNotice(恢复后核实)组成「执行纪律三闸」。

## Why(反思结论 G2,2026-08-20)

完结门禁只盯 **todos 未完成项**。谎报完成的两条路都绕过了它:

1. **不建 todos 直接谎报**:agent 对操作指令一轮零工具、纯文本回「已完成」—— todos 为空,门禁豁免,直接放行。
2. **标完不做**:todos 标 completed 但实际没执行对应写入 —— 门禁只读状态不查事实。

实测土壤:flash 类模型有「顺着对话惯性收口」倾向(3.35.0 门禁治的是「拆 3 做 1」,但「拆 0 说做完」无人管)。resumeNotice 只覆盖「恢复后首轮」,同会话内的谎报是盲区。

## What Changes

### 新门禁:**操作祈使句 + 本轮零写工具 + 纯文本非问句收尾 → 回灌核实反馈**

判定三要素(AND,全部命中才触发,精度优先宁漏勿误):

| 要素 | 判定 | 实现 |
|---|---|---|
| ① 用户消息是操作祈使句 | 动词白名单正则(**首子句动词锚定**,评审 1-8:子串匹配会误伤「确认一下刚才**改**的对不对」类核对句):`改\|加\|添\|删\|移\|换\|调\|生成\|做\|建\|搭\|重建\|重新\|清空\|设置\|配置\|美化\|优化…` | 纯函数 `detectActionImperative(text)`;**反例白名单优先且同位置锚定**:「看看\|查一下\|了解\|说说\|解释\|总结\|对比\|确认一下\|核对」等只读动词 → 非操作 |
| ② 本轮零写工具调用 | 统计本轮 tool calls:**写工具走 `writeCapable` 标注判定**(dataOps 单一真相源,不硬编码名单;editor 自定义工具由 defineTool 标注);**委派工具(`use_*`/`spawn_agent`/`spawn_agents`)计为「等效写」**(评审 1-7,否则 editor 主场景必误伤) | harness 轮内工具结果收集处计数(从零新增,评审 1-4:现有 WRITE_TOOL_NAMES 只计失败不计成功) |
| ③ 纯文本收尾且非问句 | **复用完结门禁自带的句尾正则**(`/[?？]\s*$/` 作用于收尾文本,todos.ts:84);不用 `detectQuestionIntent`(那是作用于用户消息的三档启发式,查询词档用于收尾文本会把「它的用法是…」误判问句,评审 1-1) | 复用 |

**事实清单回灌(fact-sheet,机制供给事实)**:回灌文案不是干巴巴的「请核实」,而是附 harness 从 state 计算的本轮事实清单(零额外 LLM 调用,纯本地统计):

```
本轮事实:工具调用 read×2, write×0;成功写入路径:无;失败/回滚:0;todos:0/3 完成。
```

agent 收尾声称与清单不符时无处嘴硬 —— 与项目既有哲学一致(flash 纪律靠机制不靠提示词;信息缺口走「提示随工具结果回流」)。完成说明要求**复述事实**(做了什么/改了哪些 jsonPath/组件 id/剩余什么),用户肉眼可对账。

**回灌反馈文案(双出口 + 事实清单)**:「这条指令看起来需要改动数据,但本轮事实清单:<事实清单>。如果确实已完成,请在回复中逐项说明改动位置(jsonPath/组件 id);如果尚未完成,请继续执行;如果做不到,请说明原因。」预算 ≤2(同完结门禁,防死循环),超限放行。

**挂载层与门禁协同(评审 1-2/1-3 修正)**:与完结门禁同层(createAgent 循环条件层),但**同一迭代内各回灌分支是 else-if 链式串行接力**(现有 transitional/narration/completion 全是此形态,createAgent.ts:898-918),单次迭代只有先命中者生效 —— 「同时生效」指跨迭代接力,不是一轮双回灌。可达性要点:谎报第 1 路(拆 0 说做完)恰发生在 `rounds === 0`(完结门禁有 `rounds > 0` 前置天然跳过,createAgent.ts:912),本门禁**不得带 rounds 前置**;与 narration 分支(`detectActionNarration`,同样 rounds===0 可达)的先后按声明序,先命中者 continue。四回灌预算上限:narration 2 + transitional 2 + completion 2 + zero-tool 2 = 最多 8 轮额外迭代,maxIterations=45 兜底(评审 1-11)。

### 豁免与装配边界(防误伤,评审补 P0×2)

- **子 agent 栈装配期不装本门禁**(仿 intentGuard 装配期过滤,intentGuard.ts:59;子 agent 的 task 文本必中祈使白名单,纯文本收口是子 agent 正常形态 —— craftNotes 的 `[note]` 收口恰恰是纯文本,评审 1-6)
- **委派工具计为等效写**(评审判定要素②):用户「改一下这个代码组件」→ 主 agent 调 `use_html` 委派,子 agent 在 vfs 里写,主 agent 收口「已修改」是 editor 最高频主场景,若不算写则每单烧满 2 次回灌且出口①无法机械满足
- 问号收尾/问句(完结门禁句尾正则同款豁免)
- 本轮有过写工具或委派调用但收尾没提 —— 不触发(写过/委派过就是做过)
- 用户消息含「不用改\|只是问问\|先别动\|不用写入」等明确免操作词
- **intentGuard 命中本条用户消息时跳过**(评审 1-9):「这是什么组件?顺便改成橙色」类混合消息,intentGuard 注入「先答勿做」pin 后模型守规只作答 → 本门禁若再回灌「请继续执行」就是双信号对冲;intentGuard 文案有「除非同条消息明确要求操作」逃生门,本门禁直接跳过更干净
- 空会话首轮纯闲聊(动词白名单未命中自然豁免)

### 与 resumeNotice 的协同(C-14 双保险)

刷新恢复后「重新生成」:resumeNotice(pin 段)先提示核实;若模型仍直接答「完毕」→ 本门禁兜住(零写工具 + 祈使句)回灌。**提示层 + 门禁层**两道防线。

## 设计要点

- **D1 为什么不做「终态 read 强制校验」**:每轮强制 read 烧 token 且读什么无法机械决定;零工具判定是 0 成本强信号。
- **D2 误报兜底**:预算 ≤2 后放行 + 豁免清单,最坏情况 = 多跑 2 轮,不死循环;**预算耗尽时 emit observable `ZERO_TOOL_GATE_EXHAUSTED`**(对齐 garbled 耗尽模式 createAgent.ts:887-891,评审 1-10 —— 谎报放行恰是最该让集成方感知的时刻,不能零留痕)。
- **D2b 出口①机械化(评审 1-7 延伸)**:回灌后的收口文本若含 jsonPath/组件 id 模式(粗匹配 `/child\.\d+|components\.\d+|\b[a-z0-9-]{4,}\b/` 类)即视为「已说明位置」,不再二次回灌 —— 否则委派场景「已解释」无法机械识别会恒烧满预算。
- **D3 「标完不做」(谎报第 2 路)暂不机制化**:需比对 todo 描述与实际数据 diff,语义匹配超出现有机制能力;先靠本门禁覆盖第 1 路(最高频),第 2 路登记 deferred(触发条件:真 LLM 实测出现「标记完成但数据未变」案例)。
- **D4 debugLogs 留痕**:`stage:'zero_tool_gate'`(attempt/触发消息预览),与 completion_gate 同格式。
- **D5 事实清单是「工作量总结 + 成果自检」的机制化**:agent 确认完毕时的自证不靠记忆,靠 harness 记录的对账单(工具计数/写入路径/失败数/todos 完成度)。清单只在门禁触发时随回灌注入 —— 不做每轮强制「完成报告」(常态收尾多一段模板文案 token 成本全量摊派,且大部分轮次无谎报嫌疑;风险信号命中才对账,成本与嫌疑挂钩)。若真 LLM 实测仍出现「带清单仍嘴硬」,再考虑升级为常驻收口报告(deferred)。
